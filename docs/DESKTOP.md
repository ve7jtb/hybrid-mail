# macOS app, inbox and Google setup

Launch **PQ Mail.app** from Finder. Java, OpenSSL and the patched native PKCS#11 libraries are bundled. Python 3 uses `/usr/bin/python3` by default; change its absolute path under **Keys → YubiKey configuration → Advanced** if necessary. The package is ad-hoc signed for local testing, not notarized.

## Saved identities and configuration

Settings live in `~/Library/Application Support/Hybrid Mail/`. **Show saved identity files** opens the directory. Token identities contain public signing/encryption certificates in DER and PEM, without private keys or an identity-file password. Imported software identities retain the original encrypted PKCS#12 and prompt for their password when opened. Original identity files are not moved or deleted.

The app remembers the selected identity, recipient certificate, pinned signer, sender/recipient addresses, server host/port/username, and YubiKey serial/slots. Before a PKCS#11 operation, the app checks for the configured device serial without logging in. If it is missing, **Connect your YubiKey** offers Retry/Cancel before asking for a PIN. Retry only repeats read-only enumeration; failed PIN/private operations are never retried automatically. The YubiKey operation dialog names the algorithm for the current component (ML-DSA, RSA-PSS/ECDSA, ML-KEM or ECDH). Each token operation prompts for a PIN; a composite operation reuses the PIN for its two components and clears it afterward. PINs and mailbox passwords are not saved. Google client credentials and the refresh token are saved in the Mac login Keychain under service `dev.hybridmail.google-oauth`; access tokens remain in memory. Existing local `google-client.json` configuration is migrated on first use and removed only after a successful Keychain write. Original downloaded JSON files outside app storage are not removed.

Use **Update token certificate email** to issue new local test certificates for your saved token profiles without replacing their keys. Both the subject CN and email (`rfc822Name`) SAN use the entered address. Each profile requires a signing-certificate signature and an encryption-certificate signature, with one PIN prompt each. Existing identities are retained. The new selected profile is also set as your self-test recipient and pinned signer. Export certificates with a `.pem` filename for PEM or `.cer` for DER. Certificate reissuance does not write certificates to the token or publish them online.

## Optional encryption and contact certificates

Outgoing mail is always signed. In Compose, **Sign with** selects your saved signing identity (pure or hybrid). **Encrypt to** selects a saved recipient encryption certificate when optional encryption is enabled; its label includes the mailbox, algorithm and fingerprint prefix. These two choices are independent. Signing contacts in the certificate manager are verification pins, not your outgoing private-key identities. **Also encrypt for recipient (optional)** is off by default. Signed-only mail needs no recipient certificate. Turning encryption on requires a supported encryption certificate whose email SAN matches the To address. Address mismatches are reported before requesting a PIN or SMTP credentials; the app never silently downgrades an encrypted send.

The **Certificates** tab saves contacts' signing and encryption certificates separately. Import `.pem` or `.cer`, inspect the email/algorithm/fingerprint and save it. Importing does not automatically grant trust. The import checks validity, email SAN and key usage; encryption certificates must use a supported ML-KEM profile. If a certificate has several email SANs, choose the contact address. Multiple certificates for one mailbox can coexist.

**Use selected certificate** makes an encryption certificate the current recipient, fills the To address and enables encryption. For a signing certificate it selects the certificate without changing trust or your own signing identity. **Details** shows subject, issuer, SANs, validity and full SHA-256 fingerprint. **Export** writes PEM or DER according to the filename extension. **Remove** revokes its trust and removes it from active contacts and clears a matching active pin/recipient; the public files are retained under `removed-contacts` for recovery by reimport. Removing a contact never deletes a token key or your own identity.

## Certificate fingerprint trust

The **Trust** column shows each contact certificate's status. Select a certificate and choose **Mark trusted…**, compare the full SHA-256 fingerprint with its owner, and confirm. **Remove trust** revokes the decision without deleting the certificate. Decisions persist on this Mac and multiple trusted signing and encryption certificates can coexist. Trust applies to the exact certificate DER fingerprint and purpose; a replacement certificate must be trusted separately even when it reuses the same key. The previous explicitly selected signer pin is migrated once.

After opening a successfully verified signed email, **Read & verify → Trust signer fingerprint…** shows the verified signer certificate and fingerprint for confirmation, then saves it as a signing contact and trusted fingerprint. This works for both inbox messages and local `.eml` files, including signed encrypted mail after decryption. Unsigned or invalid signatures cannot supply a trust candidate. A From/SAN mismatch remains visibly warned even when the certificate is trusted. Subsequent messages automatically check all saved signing fingerprints; no pin switching is required.

Signature validity and signer trust are displayed separately. Trust is local exact-certificate pinning, not CA path building or revocation checking. Encryption trust is a recorded verification decision; it does not block using an otherwise valid untrusted encryption certificate.

## Inbox

Select **Inbox → Connect IMAP** for a TLS server (usually port 993). The app opens `INBOX` read-only and lists up to ten newest arrivals by IMAP sequence, newest first. This is arrival order, not a global sort by the sender-controlled Date header. Only headers are initially loaded. Double-click or select **Open selected message** to retrieve the selected body (20 MiB limit). Refresh updates the list. A disconnected/stale session requires reconnecting. No delete, move, flag changes, or background polling is implemented.

Plain-text unsigned mail is explicitly marked unverified. HTML is not rendered and attachments are not displayed. Supported S/MIME mail goes through the existing signature verification and authenticated decryption pipeline; the YubiKey PIN is requested when needed. Outer headers are unprotected. Select the matching saved encryption identity before opening encrypted mail.

## Google OAuth client setup

The bundled PQ Mail Desktop client is the default for new installations. The shared project `pq-mail-ve7jtb` is in Testing and requires listed test users; Google restricted-scope verification is pending. The bundled installed-app client configuration is public, while each user's refresh token stays in the operating-system credential store. The shared client loads directly from the app without reading Keychain or Credential Manager. Custom registrations use an explicit saved selection and remain in the credential store. Reimport older custom registrations in Advanced settings to select them after upgrading.

For an optional custom client, configure Google Cloud OAuth branding, External audience and test users, enable **Gmail API**, declare only `https://www.googleapis.com/auth/gmail.readonly` and `https://www.googleapis.com/auth/gmail.send`, and create a **Desktop app** client. In **Inbox → Advanced settings…**, import its JSON or use **Advanced settings… → Enter Google client credentials…**. Then choose **Sign in with Google** and **Connect Gmail**.

Gmail uses REST over HTTPS. It lists 50 message headers per page; **Older/Newer** traverses the entire inbox and **Refresh** returns to the newest page. Only the current page's headers and navigation cursors remain in memory. Raw MIME is fetched when opened and passed to the local S/MIME verifier/decryptor; bodies and attachments are not cached to disk. Opening messages does not mark them read. Sending uses **Compose → Send… → Gmail API** and uploads the locally generated signed/encrypted MIME message. No delete, label-modify, or draft API is used. Failed or timed-out sends are not automatically retried; check Sent mail before retrying.

**Connect IMAP…** and **Send… → Other host (SMTP)** retain the existing TLS server configuration for other providers. Google OAuth remains a desktop feature; Android's preview keeps its existing IMAP/SMTP configuration.

After upgrading, select **Inbox → Advanced settings… → Use PQ Mail Google client** to switch to the shared registration, then sign in once for read/send consent. Legacy full-mail sessions are not reused. Changing scopes does not revoke an old grant at Google; remove that previous app connection in your Google account if no longer needed. Subsequently **Connect Gmail** or sending through Gmail API restores the session from Keychain and refreshes expired access tokens without opening the browser. There is no network connection on startup. macOS may ask permission to access the login Keychain, particularly after an app update. **Test Mac Keychain** checks storage with disposable data without using Google credentials.

**Sign out of Google** clears the in-memory token, deletes the saved Keychain refresh token, and disconnects the inbox; it retains client configuration and does not revoke the grant at Google. If Keychain deletion fails the app reports it; unlock the Keychain and retry Sign out. You can revoke it through your Google account's third-party connections. Never commit the downloaded client JSON, access tokens or account passwords. Google can expire or revoke refresh tokens; external OAuth projects in Testing typically issue refresh tokens that expire after seven days for the Gmail scope, so occasional reauthorization can still be required.

Signing certificates must contain the actual From mailbox in their email SAN. Encryption recipients must match the To mailbox. The original `beta0@example.test` certificates cannot sign mail with a Gmail From address; reissue local test certificates first, retaining the same keys.

Google setup and permission policies may vary by project/account. Live Gmail OAuth sign-in and IMAP inbox listing were observed in the packaged app. SMTP submission remains separately dependent on account policy and user confirmation; software tests do not establish live delivery. Sending still requires an explicit app confirmation.

References: [Google desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), [Gmail XOAUTH2](https://developers.google.com/workspace/gmail/imap/xoauth2-protocol), [Angus OAuth2](https://eclipse-ee4j.github.io/angus-mail/docs/api/org.eclipse.angus.mail/org/eclipse/angus/mail/imap/package-summary.html).

## ML-DSA-87 software identities

Choose **Keys → Create software identity…** and select Level 2, 3 or 5, matching the YubiKey profiles below. Every choice generates four software keys and saves both pure and hybrid identities in one password-protected `.p12` file. Both are remembered and appear under **Sign with**. The PQ keys are shared between the pure and hybrid profiles; importing the bundle restores both. Existing single-identity `.p12` files remain supported. Software creation does not alter token keys.

Validation: native Keychain write/read/delete passed in the packaged app. After user consent, the app was fully quit and relaunched; Connect Gmail restored its refresh token from Keychain and loaded the inbox without browser authorization. Pure ML-DSA-87 and composite ML-DSA-87/P-384 certificate, PKCS#12, signed-only and encrypted S/MIME round trips passed.

## Software versus YubiKey identities

**Software identities (.p12)** has its own selector, Create software identity and Import software PKCS#12 controls. Keys are generated in software and stored encrypted under the chosen PKCS#12 password. **YubiKey identities** has a separate selector; its entries include the required device serial. Compose also labels software versus YubiKey identities. Each token identity persists its own serial and 9c/signing, conventional-signing, KEM and ECDH slots; editing general device defaults does not rebind an existing credential. Before each private operation the app requests the bound serial if it is absent or the wrong key is inserted, without attempting a PIN on another device.

**Create identity on empty YubiKey…** offers three profiles. Level 2 creates ML-DSA-44, ECDSA P-256, ML-KEM-768 and ECDH P-256. Level 3 creates ML-DSA-65, ECDSA P-384, ML-KEM-768 and ECDH P-384. Level 5 creates ML-DSA-87, ECDSA P-384, ML-KEM-1024 and ECDH P-384. Slots are 9c / 9a / 9d / 82 respectively. Every option creates four on-device keys and saves both pure and hybrid identities; choose either when sending. The level labels refer to ML-DSA's NIST category (ML-KEM-768 is category 3). Policy is PIN Always / Touch Never. Certificates are local test certificates; private keys remain on the device.

Signing and decryption automatically use the bundled PKCS#11 backends for YubiKey identities. There are no adapter choosers; old custom adapter preferences are ignored by the desktop app. Software identities use their local private keys.

All 24 user PIV slots must have neither a key nor a certificate. The factory attestation slot F9 is excluded. Unknown metadata, unsupported firmware, communication failures and an occupied slot all stop provisioning. The native helper repeats the check on an exclusive connection immediately before generation. It has no reset/delete/import/overwrite operation. Credentials travel over stdin pipes, never command arguments or environment variables. An explicit management key or the factory AES-192 management key and the existing PIV PIN are required; credentials are not changed by this flow.

Provisioning several slots is not atomic. Failure leaves any successfully created keys in place and blocks another generation attempt. Public DER files are preserved in `token-setups`; when generation completed but certificate signing was cancelled or failed, use **Finish pending certificates…** and select that setup's `setup.properties`. This only reads and verifies the existing on-device public keys against the saved setup, then issues certificates; it never generates keys. Partially generated setups require manual recovery, not rerunning generation.

No ykman installation is needed for the packaged creation flow. It uses the bundled native Yubico yubikit helper and PKCS#11 adapters. The older Terminal scripts and optional ykman signer still require ykman. Building the helper from source requires Rust 1.88 or newer and the platform PC/SC development libraries: run `scripts/build-provision.sh` before packaging.

Software and YubiKey creation accept up to four additional comma-separated email addresses. All signing and encryption certificates, pure and hybrid, include the primary address plus these `rfc822Name` Subject Alternative Names. The subject CN remains the primary email. Duplicate or invalid addresses are rejected. Pending YubiKey setup metadata preserves the additional addresses for certificate issuance retries.

New YubiKey creation detects the inserted device and checks all user PIV slots before opening the form. The detected serial is display-only. Missing, busy, nonempty or multiple devices stop the flow; the same serial is checked again before provisioning.

Gmail **S/MIME only** filters each page using its top-level Content-Type (opaque S/MIME and multipart/signed with a PKCS#7 signature protocol). It does not fetch message bodies or establish signature validity. Pages cover 50 inbox entries before filtering, so a page may show fewer or no matches while **Older** remains available. S/MIME nested inside forwarded messages or ordinary attachments is not included.

Official desktop builds inject shared client configuration from the `PQ_MAIL_GOOGLE_CLIENT_SECRET` Actions secret. Source builds can supply that environment variable or an ignored `google-client.json` containing `id` and `secret`; without it, use the custom client import. This installed-app client configuration is extractable from the packaged app; it is not a confidential server credential. User tokens are never bundled.

### Touch ID when restoring Google sessions (macOS)

In **Inbox → Advanced settings…**, enable **Protect Google OAuth refresh token with Touch ID or Mac password**. PQ Mail asks macOS to authenticate you before reading the saved Google refresh token. Cancellation or timeout prevents restoration. This also applies when an expired in-memory session is restored; it does not prompt for every inbox request. The preference takes effect on the next restoration.

A provisioned Mac build uses Data Protection Keychain with `userPresence` access control and device-local, unlocked-only storage. Keychain requires Touch ID or the Mac password before releasing the session. Enabling the option copies the saved session into protected storage, reads it back for verification, and only then removes the legacy login-Keychain copy. Cancelling verification retains the original. Disabling protection requires reading the protected item first. No silent fallback to an unprotected token occurs on authentication failure. This does not change YubiKey PIN prompts.

Build the helper with `PQ_MAIL_APPLE_TEAM=<team> scripts/build-keychain-helper.sh`. For packaging, also set `PQ_MAIL_SIGNING_IDENTITY` to your Apple signing identity before running `package.sh`. Xcode must be signed into your developer account. The helper App ID is `io.github.ve7jtb.pqmail.keychain`; its access group is scoped to your team. Profiles and private signing material are not source files. Personal Team development profiles are short-lived and must be renewed before expiry; these are not Developer ID distribution builds.
