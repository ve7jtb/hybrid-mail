# PKCS#11 external-μ backend

This optional backend uses OpenSSL's pkcs11-provider **PR #818**, then the Rust Yubico PKCS#11 module. The tested ykman backend remains available independently. The PKCS#11 adapter never invokes ykman or falls back to software signing.

## Architecture

Bouncy Castle CMS/composite signer → 64-byte ML-DSA μ → `adapters/pkcs11-mu.py` → OpenSSL `pkeyutl -sign -pkeyopt mu:1` → PR #818 provider → `CKM_ML_DSA_EXTERNAL_MU` (`0x403C`) → Yubico PKCS#11 module → existing Beta0 PIV key.

The host already incorporates the pure/composite domain separation and ML-DSA context into μ. The adapter supplies **no `context-string`**, `--compute-mu`, `--prehashed`, or second message hash. Returned signatures are verified using Bouncy Castle, including both components of a composite signature. No PKCS#11 verification support is required.

The Yubico module maps PIV signing slot `9c` to binary `CKA_ID` `02`. The adapter explicitly selects the token using `pkcs11:serial=...;id=%02;type=private`. It first exports the corresponding `type=public` SPKI and compares it to the mail identity, so a wrong device/key fails before signing.

## Pinned dependencies

- [PR #818](https://github.com/openssl-projects/pkcs11-provider/pull/818), still open when reviewed: `joostd/pkcs11-provider` commit `8e01f28b98bb0543a9d5600ebd9e061edb21de53`.
- [Yubico/yubico-pkcs11](https://github.com/Yubico/yubico-pkcs11): `c28419969d0ac2ead2e94065b77ebbd281cc52de`; build only package `ykcs11`, using the committed Cargo.lock.
- Local build: OpenSSL 3.6.3, Rust 1.90.0, Meson 1.6.1, Ninja 1.11.1.3, Apple Clang 21, macOS ARM64. Runtime needs OpenSSL 3.5+ with ML-DSA support; other versions/platforms have not been tested here.

PR #818 is not a released provider feature yet. The Yubico module describes itself as work in progress. Their licenses remain in their source repositories; generated libraries are excluded from this repository.

## Build

First build the Java app as in the main README. Install Rust 1.90+, Meson, Ninja, pkg-config, a C compiler, OpenSSL 3.5+ development files and the module's platform prerequisites (libclang; PC/SC development libraries on Linux). No system OpenSSL configuration changes are needed.

For Homebrew OpenSSL on Apple Silicon:

```sh
export PKG_CONFIG_PATH=/opt/homebrew/opt/openssl@3/lib/pkgconfig
./scripts/build-pkcs11.sh
```

The script builds under `.deps/pkcs11`, then copies `pkcs11.dylib` and `libykcs11.dylib` into `native/` (`.so` on Linux). It does not install globally. On macOS it disables Rust post-link stripping (`CARGO_PROFILE_RELEASE_STRIP=none`) to avoid the macOS 27 LINKEDIT alignment issue tracked by [rust-lang/rust#157750](https://github.com/rust-lang/rust/issues/157750). A dynamic-load check catches unusable module binaries before hardware testing. Existing checkouts must match the pinned revisions, with no tracked changes apart from the exact supplied PIN-prompt patch. Set `HYBRID_PKCS11_DEPS_DIR` to an absolute alternate dependency directory if desired. Set Cargo/Rust cache environment variables yourself when isolating those caches.

Do not enable upstream `YKCS11_HW_TESTS`: those tests can reset PIV and erase its keys. Our test script only signs using existing keys and reads public metadata.

## Configure and test

Run from Terminal. Set the four non-secret configuration values:

```sh
export OPENSSL_BIN=/opt/homebrew/bin/openssl
export PKCS11_PROVIDER="$PWD/native/pkcs11.dylib"
export PKCS11_MODULE="$PWD/native/libykcs11.dylib"
export PKCS11_SERIAL=YOUR_TOKEN_SERIAL
./scripts/test-pkcs11.sh /absolute/path/previous-beta0-identities /absolute/path/new-output
```

The identity directory must contain the `pure.p12` and `hybrid.p12` generated by `test-beta0.sh`. These contain a token public certificate and, for hybrid signing, the software ECDSA private component; no ML-DSA private key is present. The test prompts for their existing local password, then signs one message per profile. Enter the token PIN in the app's masked PIN dialog; touch is needed only if the key's policy requires it. An `always` PIN policy may require user and context-specific login. No credentials are accepted through arguments, URI parameters, environment variables or files by this adapter.

The Java app asks for the YubiKey PIN in a masked `JPasswordField`. It caches the PIN only within one certificate/message ContentSigner operation so both composite components share one prompt. The cache is isolated for each signer and overwritten/cleared in `finally` on success or failure. Cancellation does not attempt token login. A separate operation prompts again.

The app passes a short-lived PIN copy through the adapter's stdin pipe; the adapter passes it to OpenSSL using an anonymous inherited descriptor (`-passin fd:N`). PIN values never appear in arguments, environment variables, temporary files, reports or logs. Java and Python overwrite their mutable buffers; the OpenSSL process exits after that component's signature. The provider may hold its own in-process PIN cache to handle `CKA_ALWAYS_AUTHENTICATE` login. This allows one app prompt even if a key requires both user and context-specific authentication.

The test re-parses and verifies both signed `.eml` files and writes `result.txt`. No email is sent and the signing test writes no token key or certificate. There is no automatic retry. On success it opens the mail UI with the chosen identity and adapter selected; add `--no-ui` to suppress that final window (the PIN dialogs still appear on a graphical desktop).

For later use, configure the same environment variables, run `./run.sh`, load the identity, and select `adapters/pkcs11-mu.py` under **Keys & token**. The PKCS#11 app signing path no longer needs Terminal for PIN entry. The demo launchers still use Terminal for the separate local identity-file password. Standalone adapter calls without app PIN mode use the provider's native terminal PIN prompt.

## Validation

Automated tests check the exact `mu:1` command, token/slot selection, public-key mismatch rejection, config/path injection rejection, environment override isolation, signature length, failure without retry/fallback, timeouts, and temporary-file cleanup. The existing pure/composite crypto tests also remain applicable. Hardware validation passed on 2026-11-16 with a Beta0 YubiKey using its existing ML-DSA-65 key in slot 9c. Both pure ML-DSA-65 and composite MLDSA65-ECDSA-P256-SHA512 S/MIME signatures verified through Bouncy Castle. The saved messages and signer certificates were independently reopened and verified after the interactive run. The ML-DSA component used PKCS#11 external-μ signing; the hybrid ECDSA component remained in software. No email was sent and no token keys were changed.

The build applies `patches/pkcs11-pin-prompt.patch` on top of PR #818. Terminal mode uses the provider's native hidden PIN UI instead of OpenSSL's generic passphrase prompt. App mode (`HYBRID_MAIL_PIN_STDIN=1`, a non-secret mode flag) accepts the pipe-backed callback and fails if that callback fails; it does not fall back to a second prompt.

## Both hybrid signing keys on the token

The dual-key demo uses **id-MLDSA65-RSA3072-PSS-SHA512**: ML-DSA-65 in PIV `9c`, RSA-3072 in `9a`. Configure the four paths/serial variables above, then:

```sh
export PKCS11_TRADITIONAL_SLOT=9a
./scripts/test-dual-pkcs11.sh /absolute/path/new-output
```

Both public keys are exported through PKCS#11. The demo creates fresh pure and composite self-signed certificates locally, then signs both S/MIME messages. It saves certificate-only `pure.p12` and `hybrid.p12`, with no signing private keys. A new local identity-file password is requested in Terminal. Expect four app PIN prompts: pure certificate, pure message, composite certificate, composite message. The composite operations each perform two token signatures using one per-operation cached PIN. The UI opens with the new RSA composite identity selected.

BC constructs the SHA-512 composite representative. Its RSA component uses SHA-256, MGF1-SHA-256, a 32-byte PSS salt, and trailer field 1. The host computes the RSA component's SHA-256 digest once; OpenSSL signs it using `pkeyutl -sign -pkeyopt digest:sha256 -pkeyopt rsa_padding_mode:pss -pkeyopt rsa_pss_saltlen:32 -pkeyopt rsa_mgf1_md:sha256`. The adapter expects 384 signature bytes. RSA key matching canonicalizes both public keys to PKCS#1 modulus/exponent encoding before comparison when SPKI differs; this accepts the optional rsaEncryption NULL-parameter difference introduced by composite decoding while rejecting a different key. BC independently verifies each returned component and the complete composite CMS signature.

The code also supports external P-256 ECDSA components for an existing ECDSA composite certificate; the RSA demo does not create an EC key. A certificate-only composite identity selects external signing for both components; an older identity containing a traditional private key retains that software component.

### Optional explicit no-touch provisioning

Signing scripts do not modify token keys. `scripts/provision-no-touch.py` is a separate, destructive provisioning utility: it replaces ML-DSA-65 in 9c and generates RSA-3072 in an empty 9a, both with PIN policy `always` and touch policy `never`. Run it only when replacement of 9c is intended and authorized. It refuses an occupied 9a unless it already has RSA-3072 with the requested policies. It requires a new output directory, saves public metadata and the old public key, and stops on any ambiguous device error. The old private key cannot be recovered. It does not reset PIV or change the PIN/PUK/management key.

```sh
export PKCS11_SERIAL=YOUR_TOKEN_SERIAL
export YKMAN_BIN=/absolute/path/ykman
python3 scripts/provision-no-touch.py /absolute/path/new-public-backup-directory
```

Generate fresh certificates with the dual-key demo afterward. Touch policy cannot be modified on an existing PIV key in place.

### Current validation

Software tests pass for ECDSA and RSA composite external signing, certificate-only identity save/load, invalid component rejection, exact RSA-PSS parameters, anonymous PIN-pipe transport, per-signature PIN reuse/cleanup, and provisioning guards. Hardware validation passed on 2026-11-16 for the RSA/no-touch/app-PIN flow. Both keys reported PIN policy Always and touch policy Never. Fresh pure and RSA composite certificates and S/MIME messages verified through Bouncy Castle; both saved messages and signer certificates were independently reopened and verified afterward. The RSA composite used PKCS#11 for both components. Each composite signer scopes one app PIN cache to its two component operations, then clears it. The signing run sent no email and changed no token keys; the separately authorized provisioning step created/replaced the two keys beforehand. Device identifiers, public certificates, identity files and messages remain local.
