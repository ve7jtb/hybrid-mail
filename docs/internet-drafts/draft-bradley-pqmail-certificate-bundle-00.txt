    Signed Public Certificate Bundles for Hardware-Backed Messaging
                               Identities
               draft-bradley-pqmail-certificate-bundle-00

Abstract

   This document describes a signed, compressed public certificate
   bundle used to restore hardware-backed messaging identities on
   another computer.  A bundle carries S/MIME certificates, OpenPGP
   certificates, and bindings between public keys and device key
   references.  A single-bank storage binding uses application data
   objects in a YubiKey PIV application, with a verified local recovery
   copy made before replacement.  Private keys and authentication
   credentials are excluded.  The document specifies the deployed base
   payload and proposes a separately versioned extension payload for
   additional certificate types and explicit component-to-slot mappings.
   It is intended for the Independent Submission Stream as an
   Informational document.

Discussion and implementation status

   This note is to be removed before publishing as an RFC.

   This is a working draft, not an IETF consensus specification.
   Publication in a source repository does not constitute submission to
   the Internet-Draft repository or acceptance by the Independent
   Submissions Editor.  Discussion and source:
   https://github.com/ve7jtb/pq-mail.  The compressed single-bank base
   format has been tested with PQ Mail and a separate Sequoia-based
   reader.  The extension payload in this document is a proposal;
   deployed readers do not yet accept it.  Only the current single-bank
   storage arrangement is specified.  Historical encodings and storage
   arrangements are out of scope.

1.  Introduction and Scope

   A hardware token can hold private keys without holding enough public
   identity information for a new messaging client to use them.  In
   particular, one OpenPGP composite key may involve two hardware slots,
   and an application may offer both pure post-quantum and composite S/
   MIME certificates over shared components.  A public certificate
   bundle preserves certificates, their signatures, and their hardware
   bindings without exporting private keys.

   Backup means writing public identity information to the device.
   Restore means reading that information and creating local references
   to existing device keys.  Neither operation generates, imports,
   moves, or deletes a private key.  Restore does not issue certificates
   and MUST NOT automatically grant contact trust.

   The device binding described here is application-specific.  Its
   object identifiers are not allocations from the PIV standard.  Other
   smart cards require a separately documented storage binding,
   sufficient storage, suitable key operations, and a means of
   retrieving or verifying public keys.  Having a PKCS#11 interface
   alone does not satisfy those requirements.  The format does not
   require a particular private-operation API.

2.  Conventions and Terminology

   The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD,
   SHOULD NOT, RECOMMENDED, NOT RECOMMENDED, MAY, and OPTIONAL in this
   document are to be interpreted as described in BCP 14 [RFC2119]
   [RFC8174] when, and only when, they appear in all capitals.

   A profile pairs a signing certificate with an encryption certificate
   and optional OpenPGP material.  A component is one constituent public
   key of a composite key.  A slot is a PIV key reference, not a data-
   object identifier.  A bank is the one manifest and its numbered data
   chunks.  A binding identifies which existing device key implements a
   certificate key or component.  Certificate validity, bundle
   integrity, live key matching, and correspondent trust are distinct
   results.

3.  Encoding Layers and Limits

   PIV data objects
     manifest + numbered chunks
       PQMZIP01: zlib-compressed signed envelope
         PQMAILS1: payload + signer index + signature
           PQMAILB2: deployed base profiles
           PQMAILB3: proposed base profiles + extensions

   All integers are unsigned, big-endian octet sequences.  U8, U32, and
   U64 occupy one, four, and eight octets respectively.  To match
   current implementations, a device serial is in 1..2147483647 and a
   generation is in 1..9223372036854775807.  Lengths and counts MUST be
   checked before allocation, addition, multiplication, or slicing.
   Implementations MUST reject overflow, truncation, inconsistent
   counts, and trailing bytes at every defined layer.

   BLOB(x) = U32(length(x)) || x
   ||      = octet concatenation
   MAGIC   = exactly eight ASCII octets, without a terminator

   The compressed object stream and the decompressed signed envelope
   MUST each be at most 65536 octets.  A BLOB MUST fit within its
   enclosing structure and this limit.  Zero-length BLOBs are allowed
   only where stated.  A base profile count is 2..16, including at least
   one pure and one composite profile.  These bounds are protocol
   limits, not a promise that a device has enough free storage.  Writers
   MUST account for object overhead and other applications sharing
   device storage.

4.  Compressed Container

   compressed = "PQMZIP01" || U32(expanded_length) || zlib_stream

   The stream is one zlib stream [RFC1950] containing a DEFLATE
   representation [RFC1951] of the complete signed envelope.  It is not
   a ZIP archive, gzip member, raw DEFLATE stream, or OpenPGP Compressed
   Data packet.  A preset dictionary MUST NOT be used.  Compression
   level is not fixed, so compressed bytes need not be reproducible.

   The expanded length MUST be 1..65536 and MUST equal the actual output
   length.  Readers MUST stop expansion at the declared bound, require
   end of stream and the zlib checksum, and reject additional output,
   concatenated streams, trailing compressed input, and dictionary
   requests.  No decompressed data is trusted before envelope
   verification.  An implementation SHOULD also bound CPU time.

5.  Signed Envelope

   envelope = "PQMAILS1" || BLOB(payload) || U32(signer_index)
              || BLOB(signature)

   The signer index is zero-based and selects a base profile's signing
   certificate.  The signature covers the exact payload octets,
   including its magic and all lengths.  It does not cover the envelope
   magic, signer index, compression, generation, or manifest.  Verifiers
   MUST select the indicated key, determine the permitted signature

   algorithm from its SubjectPublicKeyInfo (SPKI), and verify the
   supplied signature over the original payload bytes.  Re-serialization
   before verification is prohibited.

   The certificate issuer's signature algorithm is not the bundle
   signing algorithm.  Pure ML-DSA uses the matching pure algorithm with
   an empty application context, not HashML-DSA.  Composite signatures
   use the algorithm identified by the SPKI, including its prescribed
   hashing, domain separation, component ordering, and signature
   encoding.  Implementations MUST verify every component.  The bundle
   adds no separate signature context.  Passing a precomputed external
   mu to hardware is an implementation detail and MUST produce the same
   signature semantics.

   Writers SHOULD use the composite signing profile.  Readers MAY
   require that profile by local policy, but MUST NOT silently accept
   only its classical component.  Since the signer index is outside the
   signature, its integrity is conditional on successful verification
   with the selected key; it is not independently authenticated
   metadata.

6.  Deployed Base Payload

   base_payload = "PQMAILB2" || U32(profile_count)
                  || profile[profile_count]

   profile = U32(device_serial)
             || U8(pq_sign_slot) || U8(classical_sign_slot)
             || U8(pq_decrypt_slot) || U8(classical_decrypt_slot)
             || BLOB(signing_certificate_der)
             || BLOB(encryption_certificate_der)
             || BLOB(openpgp_public_certificate)
             || BLOB(openpgp_v4_compatibility_certificate)

   The X.509 BLOBs are nonempty and each contains exactly one DER
   certificate [RFC5280].  They are not PEM, CMS SignedData, certificate
   chains, or private-key containers.  The OpenPGP BLOBs contain binary
   public certificate packets, not ASCII armor or secret-key packets.
   Either OpenPGP field MAY be empty; a nonempty compatibility field
   requires a nonempty public certificate field.  All original
   certificate packets, including certification and binding signatures,
   MUST be preserved.

   All profiles MUST name the same device serial and the same four
   distinct slots.  Pure and composite profiles MUST share the same ML-
   DSA and ML-KEM public components.  A given slot MUST NOT be bound to
   different public keys anywhere in the payload.  Duplicate signing/
   encryption certificate pairs are invalid.  The current base profile

   places ML-DSA signing in 9c; the current creation layout uses 83, 9d,
   and 82 for the remaining fields in that order.  PIV references are
   encoded as single octets, for example hexadecimal 83 is the octet
   0x83, not the ASCII string "83".

   Legal ordinary PIV references for base fields are 9a, 9c, 9d, 9e, and
   82 through 95, hexadecimal.  This range is syntax validation only:
   the four current role assignments and supported algorithm profile
   still have to match.  Attestation and PIN/PUK references MUST NOT be
   treated as application keys.  Importers MUST NOT move keys to satisfy
   a mapping.

6.1.  S/MIME Algorithm Profiles

   Each base profile uses one row of the following table, with the
   corresponding pure or composite form for both signing and encryption.
   The OID suffixes in the last two columns are relative to
   1.3.6.1.5.5.7.6.  Level labels describe the ML-DSA category, not a
   certification of the complete system.  In particular, ML-KEM-768 is
   category 3 in both the Level 2 and Level 3 profiles.

      | Profile | ML-DSA | ML-KEM | EC    | Composite   | Composite |
      |         |        |        |       | signing OID | KEM OID   |
      +=========+========+========+=======+=============+===========+
      | Level 2 | 44     | 768    | P-256 | 40          | 59        |
      +---------+--------+--------+-------+-------------+-----------+
      | Level 3 | 65     | 768    | P-384 | 46          | 60        |
      +---------+--------+--------+-------+-------------+-----------+
      | Level 5 | 87     | 1024   | P-384 | 49          | 63        |
      +---------+--------+--------+-------+-------------+-----------+

                      Table 1: Base profile algorithms

   Pure ML-DSA SPKI OIDs are 2.16.840.1.101.3.4.3.17, .18, and .19
   respectively; ML-KEM-768 and ML-KEM-1024 SPKI OIDs are
   2.16.840.1.101.3.4.4.2 and .3.  Their AlgorithmIdentifier parameters
   are absent.  Composite identifiers and encodings follow the
   corresponding algorithm specifications [RFC10073] [COMPOSITE-KEM].
   These identifier assignments are used, not allocated, by this
   document.  Implementations MUST NOT equate similarly named
   experimental algorithms having different identifiers or encodings.

   The first composite component maps to the PQ slot, and the second to
   the classical slot.  Pure profiles map only their single component;
   the companion composite profile supplies the classical public keys.
   Readers MUST parse the algorithm's actual component encoding rather
   than treating the composite SPKI as a single device key.

   Signing and encryption certificates MUST share at least one
   rfc822Name SAN mailbox.  For activation as a messaging identity,
   validity periods and applicable KeyUsage and ExtendedKeyUsage
   restrictions MUST be checked; emailProtection or anyExtendedKeyUsage
   is required when an EKU restriction is present.  Signing uses

   authorize use of expired or revoked credentials.  CA path building
   and revocation policy remain the application's responsibility.

6.2.  OpenPGP Content and Base Slot Bindings

   OpenPGP certificates follow [RFC9580] and supported algorithm
   profiles such as [RFC9980].  Readers MUST validate self-
   certifications, subkey bindings, required signing-subkey back-
   signatures, key flags, and revocation/expiration policy before
   activating a key.  A packet's presence alone does not authorize its
   use.  Secret-Key and Secret-Subkey packets MUST be rejected.
   Unrecognized algorithms MUST NOT be guessed from lengths or replaced
   with classical operations.

   For the currently tested Level 3 separated-certification profile, the
   base format uses the following fixed additional mappings.  They are
   not additional fields in PQMAILB2.  A reader MUST recognize this
   complete profile and match every public component before activating
   it, or report the profile as unsupported.  The same logical public
   key may occur in more than one certificate view without implying
   another device key.

      +=============================+=====================+=========+
      | Role                        | Algorithm           | Slots   |
      +=============================+=====================+=========+
      | v6 certification primary    | ML-DSA-65 + Ed25519 | 86 + 87 |
      +-----------------------------+---------------------+---------+
      | v6 hybrid signing subkey    | ML-DSA-65 + Ed25519 | 9c + 84 |
      +-----------------------------+---------------------+---------+
      | v6 hybrid encryption subkey | ML-KEM-768 + X25519 | 9d + 85 |
      +-----------------------------+---------------------+---------+
      | v6 classical signing subkey | Ed25519             | 88      |
      | / v4 primary                |                     |         |
      +-----------------------------+---------------------+---------+
      | v6/v4 classical encryption  | X25519              | 89      |
      | subkey                      |                     |         |
      +-----------------------------+---------------------+---------+
      | v4 hybrid encryption subkey | ML-KEM-768 + X25519 | 9d + 85 |
      +-----------------------------+---------------------+---------+

   The v4 view uses the appropriate v4 packet encodings for its
   classical keys.  A v6 certificate and a v4 certificate have different
   primary keys and fingerprints; correspondence MUST be verified by
   their certified identities and constituent public keys, not by
   assuming their fingerprints match.  Unsupported OpenPGP profiles can
   be retained as opaque public backup data but MUST NOT become usable
   hardware identities.

   A classical-only v4 view MAY be obtained by retaining the original
   primary key, User IDs and their certifications, and the classical
   encryption subkey with its existing binding signatures and relevant
   revocations, while omitting the hybrid encryption subkey and
   signatures pertaining to it.  No signature is created and no PIN is
   needed.  The primary-key fingerprint stays unchanged.  Filtering MUST
   NOT remove a revocation or restriction applicable to a retained key,
   invent a binding, or silently change the selected cryptographic
   policy.  The resulting view MUST be verified again.

7.  Proposed Extension Payload

   This section defines a proposed, separately versioned payload.  It is
   not implemented by the deployed PQMAILB2 readers.  A writer MUST NOT
   use it for an installation that has not explicitly enabled extension
   support.  The single-bank storage, compression, and signed-envelope
   formats are unchanged.  Unknown payload magic MUST cause a clear
   unsupported-format error; a reader MUST NOT strip extensions to try
   base verification.

   extended_payload = "PQMAILB3" || U32(profile_count)
                      || profile[profile_count]
                      || U32(extension_count)
                      || extension[extension_count]

   extension = BLOB(type_identifier) || U8(flags) || BLOB(value)

   The profile encoding is exactly that in Section 6.  Extension count
   is 0..32.  Type identifiers are 1..192 ASCII octets containing an
   absolute HTTPS URI under the defining party's control.  They are
   compared byte-for-byte, are unique within a payload, and MUST NOT be
   fetched or used as executable locations.  Bit 0 of flags means
   critical; all other bits MUST be zero.  Unknown critical extensions
   cause rejection of the entire payload.  Unknown noncritical
   extensions MUST NOT affect usable identity, key selection, trust, or
   device commands.  A reader MAY retain them as opaque signed bytes.  A
   writer rewriting an imported bundle MUST preserve them or explicitly
   refuse the rewrite; silent loss is prohibited.

   All extensions are covered by the envelope signature.  Extensions
   MUST NOT override a base certificate, change its mapping, grant
   trust, designate an executable, supply credentials, or request
   provisioning.  Conflicts cause rejection.  The extension mechanism is
   additive: existing base S/MIME profiles remain required and continue
   to identify the envelope signer.

7.1.  Additional Certificate Set

   The type identifier is https://github.com/ve7jtb/pq-mail/spec/
   certificate-set/v1.  The value is:

   U32(certificate_count) || certificate_record[certificate_count]

   certificate_record = U32(certificate_id) || BLOB(format_identifier)
                        || U32(purposes) || BLOB(certificate)

   Count is 1..32.  IDs are nonzero and unique within this set.
   Purposes is a bit mask: bit 0 signing, bit 1 decryption, bit 2
   certification, bit 3 issuer-chain support.  At least one bit MUST be
   set, other bits MUST be zero, and issuer-chain support MUST NOT be
   combined with other purposes.  Purposes request local use and MUST
   NOT expand permissions in the certificate itself.  Certificates are
   nonempty and public-only.

   Format identifiers are 1..192 ASCII octets.  This version defines the
   exact identifiers "x509-der" for one DER X.509 certificate and
   "openpgp-public" for one binary OpenPGP public certificate.  Other
   formats use an absolute HTTPS URI and MUST define public-only syntax,
   key identification, signature validation, permitted uses, and
   component extraction.  Unknown formats in a critical certificate set
   cause rejection.  In a noncritical set they MAY be retained only as
   opaque data and MUST NOT be activated.

   This extension can carry additional S/MIME signing/encryption
   certificates or issuer certificates without replacing the base pair.
   Issuer-chain certificates have no private-slot mapping and do not
   become trust anchors.  The application still needs its ordinary S/
   MIME chain, identity, validity, key-usage, and revocation checks.  A
   noncritical certificate set is suitable only for information that may
   safely be ignored.

7.2.  Explicit Public-Key Mappings

   The type identifier is https://github.com/ve7jtb/pq-mail/spec/key-
   mappings/v1.  This extension MUST be critical, and its value is:





Bradley                    Expires 24 May 2027                  [Page 9]

Internet-Draft         Public Certificate Bundles          November 2026


   U32(binding_count) || binding[binding_count]

   binding = U32(certificate_id) || BLOB(key_selector)
             || U32(component_index) || U32(roles)
             || BLOB(locator_type) || BLOB(locator)
             || BLOB(component_spki_der)

   Count is 1..64.  Each certificate ID MUST refer to the certificate-
   set extension.  For X.509, key_selector is empty and selects the
   subject public key.  For OpenPGP it is the full binary fingerprint of
   the selected primary key or subkey, of the length defined for that
   key version; short key IDs are forbidden.  A component index is zero-
   based in the order defined by the certificate algorithm; a
   noncomposite key has only index 0.  It MUST NOT be inferred from
   field lengths.  For example, OpenPGP wire order and an X.509
   composite algorithm's order need not agree.

   Roles uses bits 0 signing, 1 decryption, and 2 certification, with at
   least one bit set and no other bits.  Roles MUST be a subset of the
   referenced certificate's requested purposes and its authenticated key
   flags/usages.  A tuple (certificate_id, key_selector,
   component_index) MUST appear once only; several permitted roles are
   combined in that tuple.  Every component of every key being activated
   MUST have a binding.  No omitted component may be silently downgraded
   or synthesized.

   The SPKI is the canonical DER encoding of the individual component,
   with the algorithm and parameters appropriate to that component.
   Readers MUST derive it from the referenced certificate key and
   compare it with both the supplied SPKI and the live device key.  All
   bindings naming the same locator MUST agree on the public key.  A
   binding that overlaps a base or fixed-profile mapping MUST agree with
   it exactly.

   This version defines locator_type "piv-key-reference".  Its locator
   is exactly one octet identifying an ordinary key slot on the same
   device serial as the base profiles.  Other locator types use an
   absolute HTTPS URI and need a separate specification of device
   identification, key addressing, and safe public-key matching.  An
   unsupported locator makes the critical extension unsupported.  A
   locator MUST NOT contain a PIN, management key, executable path,
   PKCS#11 module path, arbitrary command, or remote callback URL.

   These mappings permit additional S/MIME certificates, multiple
   OpenPGP keys, and other specified certificate formats without
   assuming particular PIV slots.  They do not enable a device
   algorithm, change touch/PIN policy, or prove a private key is
   nonexportable.  Import MUST show the proposed mappings for user
   review.

8.  Single-Bank PIV Storage Binding

   The YubiKey PIV application documents application-defined GET DATA
   and PUT DATA objects [YUBICO-DATA].  This binding uses object
   0x5f5000 for the manifest and objects 0x5f5001 through 0x5f5020 for
   up to 32 chunks.  These are application conventions, not globally
   reserved tags.  Writers MUST detect namespace collisions and MUST NOT
   overwrite unrelated or unrecognized data.  Standard PIV certificate
   objects are not used for the bundle.

   Object values below exclude APDU framing, status words, and PIV data-
   object TLV wrappers.  A transport adapter MUST remove only those
   wrappers, assemble ISO 7816 response chaining correctly, and supply
   exact object bytes.  USB and NFC must yield identical bytes.  Only an
   explicit object-not-found result is absence; permission failures, tag
   loss, timeouts, malformed responses, and transport errors MUST remain
   errors.

   manifest (52 octets):
     "PQMIDX01" || U64(generation) || U32(stored_length)
     || SHA256(compressed)

   chunk i at object 0x5f5001 + i:
     "PQMCHK01" || U64(generation) || U32(i) || chunk_data

   Stored length is 1..65536.  The number of chunks is
   ceiling(stored_length / 2048), at most 32.  Index i starts at zero.
   Every chunk except the last carries exactly 2048 data octets; the
   last carries precisely the remaining 1..2048 octets.  All chunk
   generations MUST equal the manifest generation.  The digest covers
   the concatenated compressed data, not the chunk headers.  Its purpose
   is complete-object consistency checking, not authentication or
   rollback protection.

   A successful write retains only this bank.  No second on-card
   recovery copy is required or written.  Unused tail chunk objects
   SHOULD be removed after local backup, subject to namespace ownership
   checks.  Hardware keys, ordinary PIV certificate objects, PIN/PUK
   values, touch policies, and other applications MUST remain unchanged.

8.1.  Read and Restore

   1.  Read the manifest; reject invalid sizes or generations.  Obtain
       each required chunk and require exact header and data lengths.

   2.  Concatenate data and verify the manifest digest.  Re-read the
       manifest and require it to be byte-identical, or report
       concurrent modification.

   3.  Perform bounded decompression and parse the complete envelope and
       payload.  Reject unsupported critical features and inconsistent
       mappings.

   4.  Verify the envelope signature and the certificate-specific
       bindings.  Check all required live public keys and the device
       serial before offering hardware identity activation.

   5.  Show mailbox identities, full fingerprints, algorithms, device
       identifier, and slot mappings for review.  Import public-only
       identities after confirmation; do not import trust, credentials,
       or executable settings.

   Reading from a file can verify signatures without a card, but the
   result MUST be labeled not yet matched to hardware.  A missing
   required key or a mismatch blocks hardware activation.  Serial
   numbers are routing hints, not cryptographic device authentication.
   Public-key matching does not prove hardware provenance or private-key
   possession; those require separate attestation or an explicitly
   authorized private operation.

8.2.  Replacement and Local Recovery

   1.  Construct and validate the replacement payload, check device
       identity and every required public key, authorize bundle signing,
       and verify the resulting signature locally.  Produce the
       compressed representation within the size bounds.

   2.  Snapshot every existing object in the owned bank.  Refuse
       unrelated data or ambiguous ownership.  If a complete prior
       bundle exists, verify and retain it as well.

   3.  Before any card mutation, save the original object bytes,
       verified prior envelope if available, replacement signed
       envelope, and replacement compressed bytes to a new local
       recovery directory.  Include lengths and SHA-256 digests.  Flush
       files, make directory entries durable where the platform permits,
       read the files back, and revalidate the replacement.  If this
       cannot be completed, stop without card writes.

   4.  Obtain management authorization locally.  Recheck the complete
       object snapshot, including absence of previously absent objects,
       and device identity before destructive work.  Serialize access
       where supported; if the state has changed, stop and replan.

   5.  Delete or invalidate the manifest first, then remove the owned
       old chunks to release space.  Do not treat a failed delete as
       success.  Write each replacement chunk and verify its exact bytes
       by read-back.

   6.  Write the manifest last.  Read the complete bank through the
       normal verification path, compare it with the intended
       replacement, and check live keys again.  Record local completion
       only after success.  Retain the local recovery copy.

   There is deliberately no atomic availability guarantee during
   overwrite: removal, interruption, or storage failure can leave no
   valid on-card bundle.  The UI MUST disclose this before backup.
   Automatic blind retries of a partially completed mutation are
   prohibited.  An explicit recovery operation MUST inspect current
   device state and the saved recovery files, recheck keys, and obtain
   any required management authorization before rewriting.  It MUST NOT
   regenerate keys or change touch/PIN policies.

   The generation increments after a valid previous generation; the
   initial generation is 1.  Writers MUST reject overflow.  A resumed
   write without a valid manifest uses the generation saved in the
   recovery transaction.  Generations are unauthenticated operational
   counters, not secure monotonic counters.  An old valid signed bundle
   can be replayed; freshness needs separate trusted local state or an
   explicitly confirmed comparison.

   Suggested recovery names are previous.pqkey, replacement.pqkey,
   replacement.pqmzip, object-TAG.bin, recovery.txt, and complete.txt.
   These names are local conventions, not wire fields.  Directory
   permissions SHOULD limit disclosure of personal identity information.
   Files MUST NOT contain PINs, private keys, OAuth tokens, management
   secrets, or trusted-contact decisions.  Recovery data MUST NOT be
   automatically published.

9.  Security Considerations

   A bundle is public, not confidential.  Anyone able to read its
   objects may learn mailbox addresses, device identifiers, certificate
   relationships, and key fingerprints.  Compression does not conceal
   this information.  Shared copies and local recovery files warrant the
   same privacy treatment as the certificates themselves.




Bradley                    Expires 24 May 2027                 [Page 13]

Internet-Draft         Public Certificate Bundles          November 2026


   A signature made by a key contained in the same bundle proves
   consistency with that key, not the owner's real-world identity.  An
   attacker can create an entirely self-consistent replacement using the
   attacker's own keys.  Live public-key checks and independently
   established correspondent trust are separate requirements.  Restore
   MUST NOT automatically mark any mailbox/fingerprint pair trusted or
   turn included CA certificates into roots.

   Bundles MUST contain only public material and declarative mappings.
   Implementations MUST reject private-key packets and prevent path
   traversal, executable configuration, automatic URL fetching, and
   command construction from certificate or extension data.  Displayed
   identity strings require escaping and length limits.  Import must
   stage all validation before persistent activation; failures MUST NOT
   leave partially trusted identities.

   Signature-valid certificates can be expired, revoked, or unsuitable
   for the requested purpose.  Removing a hybrid subkey can yield a
   still-valid classical certificate view.  Therefore signature validity
   alone does not promise hybrid capabilities or authorize a downgrade.
   Applications MUST disclose classical fallback separately for signing
   and encryption and apply their local acceptance policy.

   Storage ownership cannot be established by magic bytes alone.  Before
   deleting, the writer must inspect the namespace and its application
   context; unexpected objects require explicit recovery review.  The
   local recovery mechanism protects availability only to the extent the
   backup was durably saved and remains accessible.  The unauthenticated
   manifest and generation permit denial of service and rollback.  No
   claim of transactionality across power loss is made.

   Readers MUST bound decompression, parsing, certificate counts, packet
   nesting, and signature work.  Failed hardware reads MUST NOT be
   converted to missing objects or empty slots.  A restore operation
   requires no signing PIN or private operation in this storage binding.
   An application MUST NOT retry a PIN after rejection or modify key
   policy to complete restore.

10.  IANA Considerations

   This document requests no IANA actions.  The PIV object tags and
   extension identifiers are application-specific conventions and do not
   reserve a PIV namespace, an IANA registry, an OID, a URI scheme, or a
   media type.  Existing cryptographic identifiers retain their
   specifications.  The local file suffixes .pqkey and .pqmzip do not
   establish registered MIME types.

11.  Implementation and Interoperability Status

   As of 20 November 2026, a Level 3 bundle using the deployed base
   payload was written to a single bank on a PQC Ready YubiKey Beta0,
   restored into a fresh PQ Mail store, and independently read and
   verified with a Sequoia-based adapter.  The tests compared public
   keys and PIN/touch policies before and after.  This establishes
   interoperability for that tested profile, not universal hardware
   support or a production security audit.

   The companion public software fixture uses synthetic identities and a
   synthetic serial; no private keys or actual user's hardware backup
   are included.  It exercises pure and composite envelope signatures,
   compressed framing, and separated certification/signing keys.  The
   extension payload, other-card bindings, and all possible certificate
   algorithms require additional implementation and interoperability
   testing.

Appendix A.  Companion Test Material

   The repository accompanying this draft includes a public-only
   software fixture, a framing validator, and build instructions.  The
   fixture contains both pure-signed and composite-signed compressed
   base bundles and the expected component SPKIs.  It MUST NOT be used
   as a production identity.  The framing validator does not replace
   cryptographic signature verification; independent signature
   validation uses the Sequoia adapter test suite.

   Negative tests should include truncated chunks, wrong indices/
   generations, digest mismatch, invalid zlib boundaries, expansion
   overflow, trailing bytes, invalid signatures in either composite
   component, secret OpenPGP packets, invalid bindings, wrong device or
   key, conflicting mappings, unknown critical extensions, namespace
   collisions, and interruption after every mutation step.  A successful
   reader must not perform a private-key operation or confer contact
   trust.
